## 模块划分与原因

采用模块化单体：HTTP入口、应用服务、领域对象、持久化适配器分层。账号认证、商品审核、预约交易、信用答题、举报评议、统计日志六个模块在同一应用进程内，通过明确服务接口交互。相较于拆成微服务，这个规模更需要单数据库事务和容易联调的代码结构。

买家与卖家是同一User的业务角色，不是互斥的继承子类。管理员通过角色授予，所有权和认证状态仍按操作校验。管理端导航只向管理员展示，设计稿为了展示全部模块统一列出入口，不代表普通用户获得管理权限。

Product管理生命周期；Reservation仅表示意向；Invitation表示当前卖家选择及截止时间；Trade在买家接受后创建，保存锁定标价。不能用单一布尔“已预约”替代这四种含义。

取消、超时和完成由TradeService组织事务，领域对象拒绝非法转换。CreditService借助PenaltyPolicy接口区分7天取消与30天爽约策略；从事件账重放分数，避免仅保存总分导致无法更正。

## 存储形式与唯一约束

使用PostgreSQL保存结构化数据，对象存储保存图片。金额用定点decimal，时间存UTC时间戳；展示与答题日界线转换为Asia/Shanghai。商品图片可以公开获取；校园卡及证据只能通过后端逐次鉴权下载，不把永久公开地址放入页面。

| 表或集合 | 关键字段与关联 | 约束 |
|---|---|---|
| users、roles、user_roles | id、username、password_hash、status；用户与角色多对多 | username唯一；角色由平台授予 |
| verifications、student_bindings | user_id、姓名、学号、card_asset_id、状态；绑定关联用户 | 已通过的学校学号唯一；同一用户仅一个有效绑定 |
| products、categories、product_images | seller_id、category_id、标题、描述、price、状态、version、first_published_at | 价格0.01～99999.99；正式发布校验完整性 |
| reservations、invitations、messages | buyer_id、product_id、预约状态；邀请关联预约及deadline；留言关联预约 | 有效预约的(product_id,buyer_id)唯一；每商品最多一个当前有效邀请 |
| trades | product_id、buyer_id、seller_id、invitation_id、locked_price、deadline、双方确认字段 | 同商品在锁定、单方确认、争议状态下最多一笔有效交易；invitation_id唯一 |
| credit_accounts、credit_events | user_id、trade_id、kind、amount、occurred_at、revoked、版本与更正关联 | 信用账以(occurred_at,id)排序；同事件来源不重复写入 |
| quiz_attempts、quiz_questions | user_id、北京时间日期、答案、得分、关联恢复事件 | (user_id,local_date)唯一；题目引用避免事后改答案影响历史 |
| moderation_cases、case_evidence、appeals、votes | 举报对象、双方、状态、脱敏摘要、决定；证据关联media_asset | (case_id,voter_id)唯一；每案允许的申诉次数及截止需事务校验 |
| product_views、audit_entries、idempotency_requests | 浏览者、商品、时间；操作者、动作、对象、结果；请求键及请求摘要 | 浏览统计按窗口去重；幂等键按用户、动作、键联合唯一 |
| media_assets | owner_id、object_key、真实格式、大小、access_scope、绑定状态 | 不公开私密对象键；事务未绑定的暂存文件清理 |

数据库层用唯一约束或部分唯一索引兜底，但不能代替服务层检查认证、当前邀请及截止时间。历史交易和邀请保留多条，唯一限制只作用于当前有效子集。

## 核心事务与接口边界

| 场景 | 建议接口/服务 | 同步修改 |
|---|---|---|
| 注册登录、认证 | POST /accounts、/sessions、/verifications | 用户、会话、认证申请、学号绑定及日志 |
| 商品提交、复核 | POST /products/{id}/submit、/review | 商品、审核结果、有效预约和邀请、日志 |
| 发起意向、改选 | POST /products/{id}/reservations、/invitations | 预约、当前邀请、旧邀请失效及日志 |
| 接受邀请 | POST /invitations/{id}/accept | 锁定商品、创建交易及价格快照、结束其他预约、幂等结果、日志 |
| 取消、完成、到期 | POST /trades/{id}/cancel、/confirm；expire(now) | 交易、商品、预约、必要的信用事件及日志 |
| 举报裁决、更正 | POST /cases、/cases/{id}/decision、/appeal | 案件、交易状态、账号限制、信用事件重放及日志 |
| 答题提交 | POST /quiz-attempts | 当日答题唯一记录、恢复事件和信用账 |
| 查询、统计与日志 | GET /products、/me/stats、/audit | 只读，依用户权限过滤 |

接受邀请先按当前用户和动作检查幂等键及请求摘要。已有成功结果且参数相同，直接返回原tradeId；同键不同参数拒绝。新请求锁定商品行，再校验当前邀请、权限和截止时间，然后同一事务更新全部关联对象。不同买家通过商品行锁顺序校验；重复同键通过请求记录唯一约束串行处理。鉴权必须先于读取他人的幂等结果。

到期任务、取消和完成也须按同一商品/交易锁顺序更新。任一方已确认则禁止直接取消和超时释放；管理员处理争议可解除或完成。部分写入失败全部回滚，失败安全审计另写拒绝事件。统计直接以有效完成交易查询，不在前端累加。

商品图片先上传暂存，业务提交绑定引用；失败后清理孤立对象。每日备份以数据库和媒体引用清单一起核验，私密媒体访问仍需鉴权。

## 边界、技术判断与待确认项

本实验不实现支付、物流、实时聊天、校园统一认证或图片内容自动审核。UI中所有姓名、学号、案件与商品均为演示样本。

PostgreSQL、对象存储、模块化单体、行锁和接口路径最初由AI提出，本人已反馈全部保留；保留理由由AI整理，不冒充本人逐字论证。参考硬件、并发验收与备份要求继承实验一，不声称已实际测试。

校园卡留存期限、身份更正与找回证明、密码复杂度和找回方式仍继承实验一的待确认状态。设计暂保留可配置策略与人工入口，不自行补造已确认规则。校园卡审核不能保证完全防止冒用。
